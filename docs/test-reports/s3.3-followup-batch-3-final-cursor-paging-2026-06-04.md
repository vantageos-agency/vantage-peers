## Migration — list_peers cursor strategy

**Pattern**: identical to batch 1 + batch 2 (newest-first forward pagination with `createdBefore` anchor on `_creationTime`).

MCP wiring (`mcp-server/src/tools.ts` ~line 1590):
- Schema: `+ cursor: z.string().optional()`.
- Handler: `decodeCursor → createdBefore`, `clampLimit`, forwarded to `profiles:listProfiles` with `createdBefore`.
- Payload mapping now exposes `_id` + `_creationTime` on each peer so the `nextCursor` anchor can be computed from the last row.
- `nextCursor` emitted via `encodeCursor({ createdBefore: last._creationTime })` only when the returned page is full.

Convex query (`convex/profiles.ts: listProfiles`):
- Added `limit: v.optional(v.number())` and `createdBefore: v.optional(v.number())` args.
- Refactored from unbounded `.collect()` (both branches: with `orchestratorId` filter and without) to `.order("desc").take(take)` + post-take `r._creationTime < createdBefore` filter.
- Default `take = limit ?? 50` (doctrine-aligned ceiling; matches the unbounded-`.collect()` fix applied to `githubRepoMapping:list` in batch 2).
- Added `import type { Doc } from "./_generated/dataModel"` with the canonical hint marker `convex-strict-mode-doc-type-import-needed-when-refactoring-list-query-from-early-return-to-accumulator-post-filter` for future grep audits.

### Why list_peers was tractable

The brief flagged a concern: profiles backend had `.collect()` with no ordering. Resolution: profiles documents carry the system `_creationTime` field (every Convex doc does), so we can apply the **same** `createdBefore` anchor as every other batch-1/batch-2 tool — no alternative cursor strategy needed, no deferral. The refactor only required adding `.order("desc").take(limit)` to materialize the chronological page before the post-take filter.

## Doctrine exceptions — explicit JSDoc markers

Each exception carries an `@cursorPagingException <reason>` marker directly above its `server.tool(...)` call so future contributors and audit scripts can find them with `grep -nE '@cursorPagingException'`.

### list_broadcast_status — `@cursorPagingException single-object-shape-not-list`

Returns a single status object — `{ messageId, from, channel, createdAt, receipts[] }` — not a top-level array. Cursor paging is defined on top-level arrays, not embedded sub-arrays of a single envelope. Migrating would require a separate `list_broadcast_receipts` tool, which is out of scope for the S3.3 B8 rollout.

### search_components — `@cursorPagingException relevance-ranked-not-chronological`

Results are scored by query similarity (`convex/components.ts: search`). A `createdBefore` anchor would skip high-relevance older matches in favor of newer low-relevance ones, breaking the search contract. Pagination on semantic search should be score-based (offset / topK), not time-based — separate workstream.

### search_fix_patterns — `@cursorPagingException semantic-action-not-chronological`

Backed by `convex.action("search:searchFixPatterns")` which runs an embedding-similarity ranker. Same rationale as search_components. Note the action-backed (not query-backed) call path — even the cursor-decode plumbing would be different.

## Backward compatibility

- `list_peers` keeps its `?? 20` default at the MCP wrapper, so callers that omit `limit` keep the pre-batch page size.
- `listProfiles` `createdBefore` is `v.optional`; pre-batch callers never pass it.
- `listProfiles` `limit` is `v.optional` with server-side default `50`, replacing an unbounded `.collect()`. Existing callers that previously got the full profiles table (typically a small number of orchestrators in production) keep getting their full result unless they exceed 50 — doctrine-aligned ceiling consistent with `githubRepoMapping:list` (batch 2).
- `nextCursor` is added to the envelope only when the returned page is full. Callers that ignore `nextCursor` see no behavioral change.
- Doctrine-exception tools have **zero** code change to their handlers or schemas — only JSDoc markers were added.
