## RED → GREEN evidence

### RED — 21/35 FAIL

Test plan per tool: 5 tests (T1 master, T2 non-master in-scope, T3 legacy bearer, M1 cross-tenant, M2 own-tenant).

| Test class | Cardinality | Expected status at RED |
|---|---|---|
| T1 — master scope | 7 (one per tool) | PASS (guardMasterOnly is a no-op for master) |
| T3 — legacy bearer (`oauthCtx === undefined`) | 7 | PASS (no-op for undefined ctx) |
| T2 — non-master in-scope | 7 | **FAIL** (Forbidden envelope returned) |
| M1 — cross-tenant non-master | 7 | **FAIL** (Forbidden envelope returned) |
| M2 — own-tenant non-master | 7 | **FAIL** (Forbidden envelope returned) |

Total: 14 PASS + 21 FAIL = 35. RED failure surface is uniform: `mcpError("Forbidden: <toolName> requires master scope (current: <profile>).")` short-circuits the handler before any scope-filter can run, so the response carries `isError: true` and a `Forbidden:` body. The negative-path assertion `expect(isForbiddenResponse(res)).toBe(false)` therefore inverts at GREEN.

### GREEN — 35/35 PASS

At `0d01bc1`, each tool's handler:
1. Drops `const _scopeDenied = guardMasterOnly("<tool>");` + early-return.
2. Forwards the Convex result through `scopeFilterList` (for list_*) or `scopeFilterGet` (for get_*).
3. Renders the filtered slice via the same `capListResponseBytes` / `JSON.stringify` pipeline (no envelope semantics changed).

Special note for `list_issues`: the handler builds `results` from one of four Convex query branches based on filter combination (`assignedTo` / `project` / `status` / default). The filter is applied to the materialised `results` array immediately before rendering, so all branches are covered uniformly without duplicating the filter call per branch.

Full mcp-server suite at GREEN: **137/137 PASS** (102 carried from C1 SHA `03f4d251` + 35 new C2 tests). Zero regression.
