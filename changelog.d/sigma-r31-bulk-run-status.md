- **`bulk_complete_tasks` runs now have a status a client can read, so a failed later batch is no longer silent.** `bulkComplete` closes its first 500 in the call and drains the rest through a scheduled continuation; there is no caller to throw at, so each live run now writes a `bulk_complete_runs` row keyed by the `bulkRunId` the first call already returned (`status` running / complete / failed, `closed`, `remaining`, `failureReason`, `orgId`, `createdBy`). New query `tasks:getBulkCompleteRun` and MCP tool `get_bulk_complete_run`: served to the run's own organisation on the Convex side and, at the MCP layer where the caller is the service account, gated on the row's org and on its creator (`scopeFilterGet`); another org, another creator and an unknown id all answer "not found", and an anonymous Convex caller is refused `RBAC_DENIED`. A later batch that fails (RBAC or closure gate) now records `failed` plus the reason on the row instead of ending as a bare scheduler failure, closes nothing past the refusal, and re-calling the same filter meets the same refusal. The return shape of `bulk_complete_tasks` is unchanged. bulkCompleteSelfScheduled 10/10 (5 RED before) and get_bulk_complete_run 7/7 on the MCP side. **The run's org comes from the verified principal, never from a name or a member's argument.** Through MCP the Convex scope is the service account (master, no org), so the transport forwards the bearer's verified org (the agent credential's org, else the org on its access-token row) as `verifiedOrg`, on the same trust rule as `verifiedPerson`: `bulkComplete` honours it from the fleet service account only (any other caller presenting it is refused `RBAC_DENIED`, preview and live alike), resolves it against an active `client_org_mapping`, and stamps the run row with it (`convex/lib/verifiedOrg.ts`). `get_bulk_complete_run` then serves a non-master caller only a run whose org equals the caller's own resolved org; a run with no org (a fleet-master run) is not served to a non-master caller, and the creator name is only an extra intersect. **A real cross-tenant write, measured and closed for `bulkComplete`:** orchestrator names are not unique across orgs, and through MCP the scan is master-scoped with only a creator/assignee NAME check, so an org-a "eta" closed org-b's "eta" tasks (10 matched where 5 belong to org-a; a >500 drain closed 30 org-b rows). With a `verifiedOrg` the match set, the dry-run count and every continuation batch are now narrowed to tasks stating that org; without one (master / fleet path) nothing changes. bulkCompleteVerifiedOrgNarrowing 3/3, RED 2 before. **The ten single-task doors with the same collision are closed in the follow-up fragment `sigma-task-doors-verified-org.md`.**
