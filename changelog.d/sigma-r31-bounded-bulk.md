- **Every mutation that read an unbounded set now bounds the read and continues through the scheduler (backend-doctor R-31).** Measured with the doctor itself: the read half had 18 violating sites, it now has 0, and R-31 is no longer in MECHANICAL VIOLATIONS (7 to 6). `renameAgent` rewrites an agent's relation edges 100 per side per transaction (`renameAgentRelations`); `bulkComplete` schedules `bulkCompleteContinue` after its first 500, with the same return shape, tenant scope, creator/assignee check, closure gate and completion note; a failed continuation logs its run id and reason and ends "failed", and re-calling the same filter meets the same refusal in the foreground. `markDocSoftDeleted`, `cascadeCloseMission`, `processDueTasks` and `dedupStaleDeployTasks` batch and self-schedule (the mission is marked complete only after its last task closed; the dedup sweep carries only the deploy-titled tasks between pages). `tasks:complete` answers "is every task of the mission done" with two `take(2)` index ranges either side of `done`; `createDeployTaskWithDedup` reads through `by_project` (a same-titled task filed under another project is no longer scanned); the agent-roster clash check refuses over 500 agents instead of reading them all. On the oauth surface `deleteClient`, `patchClientScopeAndRefreshTokens` and `revokeAccessTokensOnly` walk a client's tokens 500 per table per transaction with a cursor (`continueClientTokenWalk`), the profile-rename client retarget runs in batches (`continueClientRetarget`), and the retrofit's live-refresh-token check streams newest-first and stops at the first live row, so a live token can never hide behind dead ones. Every oauth refusal path is pinned unchanged (148 oauth tests before and after, plus 11 new). **Named and not closed:** (1) the read half of R-31 reads could-not-judge, not present, because 39 bounded `.take`/`.paginate` reads (mostly caller-driven migrations) have no `runAfter` in the same mutation block and the detector cannot decide them; none is a violation. (2) `oauth_access_tokens` validation consults the token row's `revokedAt`, not the client's, so for a client holding more than 500 tokens in a table the tokens past the first batch are revoked or retargeted moments after the call returns, not inside it; no client in practice holds that many. (3) Counts a mutation returns are those of its first transaction.
