- **Client ID Metadata Documents at `/authorize` and `/token` (Cloud MCP; mcp-doctor S5 (g) / S-46, task k174expfdyh954kzynmt9tyv9d8hxa1s).** An unregistered, URL-shaped `client_id` (Claude.ai's `https://claude.ai/oauth/mcp-oauth-client-metadata`) is resolved by fetching its document (draft-ietf-oauth-client-id-metadata-document-00; MCP authorization 2025-11-25) instead of answering `unknown-client`; the AS metadata now announces `client_id_metadata_document_supported: true`. SSRF bounds: https only on the default port, no userinfo, fragment, dot segments or IP-literal host in the `client_id`; DNS resolved once here, every answer must be public (private, loopback, link-local, CGNAT, multicast, reserved, cloud-metadata, and IPv6 forms embedding them are refused) and the socket is opened to that validated address, with the certificate checked against the hostname (no rebinding window); no redirect followed; body capped at 5 KB (declared and streamed); 3 s budget for DNS, connect and body; `Content-Type` must be JSON; at most 8 fetches in flight; cache bounded to 256 documents and a 1 h ceiling (5 min default, `no-store` honoured), errors and invalid documents never cached. The document must carry `client_id` equal to the URL, `redirect_uris` (exact match, no wildcard) and `token_endpoint_auth_method: "none"` (no `client_secret`); a refusal answers 400 `invalid_client` with `client-metadata: <reason>`. The document grants nothing: the token's rights come from the signed-in person and the organisation mapping, as for every client. Registered (DCR) clients keep their path and are never fetched. No Convex function or argument changes. Tests: `mcp-server/test/cimd-resolver.test.ts`, `mcp-server/test/cimd-authorize-token.test.ts`. Hardening after the dev-sentinel audit: `/authorize` can use at most 5 of the 8 fetch slots (3 are reserved for `/token`, so a person's refresh still resolves under a flood); one source address may start 10 fetches per minute, separately for `/authorize` and `/token` (cache hits are free; 429 `rate-limited` with `Retry-After`). Deviation from draft §4.4, stated: failed hosts are NOT negatively cached, because errors stay uncached as the draft requires; the starvation is bounded by the per-source limit plus the reserved slots, and a negative cache keyed on a URL the attacker chooses would not bound it. A failure that may pass (DNS, timeout, 5xx, busy, rate limit) answers 503 `temporarily_unavailable` so a client keeps its refresh token; only a wrong document is 400 `invalid_client`. The consent page names the redirect origin and flags the client as unverified; bidi, zero-width and format characters are stripped from `client_name`; the IPv4-mapped and SIIT ranges are refused, a trailing dot no longer hides `localhost.`, a `client_id` is capped at 512 characters, `/authorize` resolves the document once, the cache is a true LRU, and a refresh naming another `client_id` than the one it was issued to is `invalid_grant`. Revocation: `POST /admin/oauth/document-clients/deny` (`client_id`, `reason` of 20+ characters, `operator`, served by the existing `oauth:deleteClient` door: deleting a URL client lists it) lists a client in the new `oauth_denied_document_clients` table, revokes every access and refresh token it holds, and `/authorize`, `/token` and refresh refuse it before any fetch (a list that cannot be read answers 503, fail closed); `getAccessTokenByHash` also refuses any token row of a listed client (derived live, rights-derivation: the listing reaches tokens minted before it by construction). Lifting a listing is the operator deleting the row in the Convex dashboard (a new write door would raise the R-53 ratchet); revoked tokens stay revoked. Backend contract version 26 (Convex first, then the MCP). Tests: `convex/__tests__/documentClientDenial.test.ts`, `mcp-server/test/cimd-authorize-token.test.ts`. Second audit round: each path has a fetch pool no other can take (authorize 3, token 3, refresh 2); one source may have 2 fetches in flight per path and is keyed on its IPv6 /64 (IPv4 in full); one registrable domain holds at most 2 fetches whoever asks, and concurrent resolutions of one document share one fetch. A refresh that names no `client_id` is refused (the token is not spent). The deny-list is read by one helper at every token reader (`getAccessTokenByHash`, `resolveVerifiedPerson`, both `orgRoster` token readers). `POST /admin/oauth/document-clients/allow` unlists through the same `oauth:deleteClient` door (`lift`), keeping every listing and unlisting (who, when, why) in the row's history; a `client_id` not in canonical form is refused, and a listing that revoked no token carries a warning. `3fff::/20`, `2001:10::/28` and `2001:20::/28` are blocked; `client_name` is folded to NFKC with typographic spaces made ASCII. Third audit round: the per-domain bound keys on the registrable domain from the Public Suffix List (`tldts`, private suffixes included, trailing dot stripped; `evil.vercel.app` no longer shares a bucket with `victim.vercel.app`, `a.one.com.` no longer shares `com.`), and the refresh path has no domain bucket at all. The audit of the deny-list moved from an array on the deny row to its own table, `oauth_document_client_events`, one row per listing or unlisting; `reason` is capped at 500 characters and `operator` at 120. Known limit, reasoned and not measured: a code exchange already past its deny-list check when the operator unlists (or lists) the client can complete once with the state it read; the next check, and `getAccessTokenByHash` at every request, apply the new state. Fourth audit round: a hostname must be real (every label LDH, none empty, punycode allowed, and a registrable domain must exist), so `x1..a.example` and `x2..a.example` can no longer be two domain keys; the key is never the whole host. The refresh pool is kept per connection (at most one fetch in flight per refresh token) with a small global cap of 2, and a refresh of a known client is served the cached document for up to 1 hour past its TTL (`CIMD_STALE_MS`) when its fetch is refused by load or fails in a way that may pass (busy, rate limit, DNS, timeout, 5xx); a document that is now wrong (invalid, wrong auth method, client_id mismatch) is never served stale, `no-store` documents are never cached so never stale, and a listed client is refused before any cache is read. `reason` and `operator` over their caps answer 400 on the admin route. `tldts-core` is pinned exactly beside `tldts` (7.4.19 declares `tldts-core` as `^7.4.19`, a range). The deny-list table `oauth_denied_document_clients` has never been deployed, so no production row carries the earlier `history` array: `git grep -c oauth_denied_document_clients origin/main -- convex/schema.ts` exits 1 with no match. Known limit: a suffix missing from the bundled Public Suffix List snapshot is treated by `tldts` with the default rule (the last label is the suffix), so two tenants of such a suffix share a domain bucket until `tldts` is bumped. Fifth audit round: the cache reflects the latest successful fetch (a `no-store` or `max-age=0` fetch DELETES the older entry, so a document that dropped a redirect URI is never served stale with the old one), and one person has at most one refresh fetch in flight over all their connections (on top of one per connection). Known limit: every limit here (pools, per source, per person, per connection, the document cache) is per process, so with several Railway replicas they multiply by the replica count.
