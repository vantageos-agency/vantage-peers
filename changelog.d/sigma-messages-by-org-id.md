- **The messages family admits and selects rows by the organisation's permanent ID, not its slug (VantagePeers Cloud).** `listMessages`, `listByChannel`, `listByChannelPaginated`, `getById`, `searchMessagesByKeyword`, `listBroadcastStatus`, `listMyInbox`, `getUnreadCount`, `markAsRead`, `deleteMessage`, the inbox readers behind `checkNewMessages`/`checkNewMessagesEnvelope`, the person-recipient proof of `sendMessage`, the dashboard summary and the improvisation digest compared a row's `tenantId` with the caller's slug, a renamable label: an organisation that took a slug released by another read, marked and deleted the previous holder's messages and receipts. They now compare `tenantOrgId` with the caller's verified org ID (the `*_clerk_id` indexes). A row with no `tenantOrgId` belongs to no organisation: unstamped fleet rows stay visible to the fleet reader only, rows that name a slug but no ID are withheld from every caller except the master. A caller whose mapping carries no ID reads nothing. The blocker notice written when a task a waiter depends on closes is stamped with a client waiter's org (a fleet waiter's stays unstamped). The `search_content` index gains `tenantOrgId` as a filter field. No public argument or return change. Run the `tenantOrgId` backfill and check its coverage count before deploy: a row not yet stamped disappears from its organisation's reads. Pinned by `convex/__tests__/slugTakeoverMessages{Reads,Inbox,Write}.test.ts` and `convex/__tests__/blockerNoticeTenantStamp.test.ts`.
