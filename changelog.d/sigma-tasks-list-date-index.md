- **`list_tasks` with `updatedSince`, `createdBy` or a `createdBefore` cursor is answered from an index range instead of refusing with `SCAN_CAP_EXCEEDED` (task k171t66wdznjztdpb8dby6f86h8hsx61).** Measured on prod 2026-11-07: `list_tasks {status:[done], updatedSince, limit:200}` failed because the 2000 newest `done` rows were read before the date filter ran, and `assignedTo` + `status` failed for the largest assignees. Each status bucket is now one index range (tenant or assignee first, then the date bound), newest-created first, with the same opaque `nextCursor`. Still refused loudly, never a partial page: an `updatedSince` window that itself holds more than 2000 rows (shrink the window); `createdBy` together with an assignee, a project or an instance; `updatedSince` together with a project or an instance, on a bucket above 2000 rows. Six indexes added on `tasks` (`by_orgId_status_updatedAt`, `by_orgId_createdBy_status`, `by_assigneeId_status`, `by_status_updatedAt`, `by_createdBy_status`, `by_status_creation`) and seven label-keyed indexes with no reader dropped (32 to 31 of the 32 allowed). No Convex argument changed; backend contract stays 19. Test: `convex/__tests__/tasks-list-date-index.test.ts`.
