- **`list_tasks` with `updatedSince`, `createdBy` or a `createdBefore` cursor is answered from an index range instead of refusing with `SCAN_CAP_EXCEEDED`; an `updatedSince` window of any size now pages complete (task k171t66wdznjztdpb8dby6f86h8hsx61).** Measured on prod 2026-11-07: `list_tasks {status:[done], updatedSince, limit:200}` failed because the 2000 newest `done` rows were read before the date filter ran, and `assignedTo` + `status` failed for the largest assignees; 981 `done` tasks were already updated since 1 November, so a month-long period audit would have been refused again by a whole-window read under the 2000 cap. Each status bucket is one index range (tenant or assignee first, then the date bound). With `updatedSince` the rows are served NEWEST-UPDATED FIRST (index order: `updatedAt` desc, then `_creationTime` desc) instead of newest-created first, and `nextCursor` resumes exactly at the last row's pair (`updatedAt`, `_creationTime`): the opaque token is versioned (`{v:2, createdBefore, updatedAt}`), a token minted before still decodes to `createdBefore` alone, and the MCP forwards the new optional Convex argument `updatedCursor` (requires `createdBefore`). Multi-status requests merge the per-status ranges by that same pair, so one position resumes all of them. Declared limits, refused loudly with the remedy in the message and in the `list_tasks` description, never a partial page: `assignedTo` together with `createdBy`, and `project` or `assignedToInstance` together with `createdBy` or `updatedSince`, on a bucket above 2000 rows (drop one key or narrow by `status`); `createdBy` over an `updatedSince` window when more than 2000 rows must be read to fill a page, which includes the last page of a creator's rows in a window above 2000 (no index carries the creator with `updatedAt`; raise `updatedSince`, narrow by `status`, or drop `createdBy`); an `updatedSince` window resumed with a createdBefore-only cursor above 2000 rows (repeat the query without the cursor). Six indexes added on `tasks` (`by_orgId_status_updatedAt`, `by_orgId_createdBy_status`, `by_assigneeId_status`, `by_status_updatedAt`, `by_createdBy_status`, `by_status_creation`) and seven label-keyed indexes with no reader dropped (32 to 31 of the 32 allowed). Backend contract version 19 -> 21 (`BACKEND_CONTRACT_VERSION`, `REQUIRED_CONTRACT_VERSION`; 20 is taken by PR #1702): ROLLOUT Convex first, MCP last (`.claude/rules/railway-mcp-redeploy.md`); the argument is optional, so the live MCP keeps working until it ships. Tests: `convex/__tests__/tasks-list-date-index.test.ts` (2500-row window, 2400 rows tied on `updatedAt`), `mcp-server/test/list-tasks-updated-since-cursor.test.ts`.
