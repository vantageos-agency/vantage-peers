section: Security
---
- **VantagePeers Cloud `/authorize` no longer auto-approves: a code is issued only to a signed-in Clerk person who picked one of their own organisations and approved.** Before, any registered client got a code with no user and the code's user was `client.scopeProfile`, so Claude.ai or ChatGPT connected as an anonymous app. Now `GET /authorize` redirects to Clerk sign-in, then shows a server-rendered org picker and consent page (`POST /authorize/org`, protected by the `consentToken`), and `POST /token` mints the access token from the claims `{sub, org_id, org_slug, org_role, aud, client_id}`; authority is resolved through `client_org_mapping` by the org slug, never from the client's scope profile. A replayed code is refused and revokes the token it issued. No refresh token on this flow. New `GET /authorize/callback`, `GET /userinfo`, `/.well-known/openid-configuration`. Fail-closed: a missing `AUTHORIZE_STATE_SECRET`, `CLERK_DOMAIN`, `AUTHORIZE_SIGN_IN_URL`, `AUTHORIZE_CALLBACK_URL`, `PUBLIC_BASE_URL` or `CLERK_SECRET_KEY` answers 503. Convex: table `oauth_person_codes` (digest, atomic `oauth:consumePersonCode`), `oauth:putPersonCode`, `oauth:revokeAccessTokensForCode`, hourly purge cron, `codeHash` on `oauth_access_tokens`. Requires `@vantageos/cloud-identity` ^0.8.0. Deploy Convex first (additive), then the MCP server. Evidence: `mcp-server/test/oauth-authorize-requires-user.test.ts` 37/37, red 34/37 on d440b95.
