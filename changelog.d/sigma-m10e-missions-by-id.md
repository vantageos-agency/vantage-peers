- **Missions decide on agent IDs, never on names (module M10e).** `missions:create` and `missions:update` resolve the pilot, participants and creator to agents-row IDs of the mission's own org (`pilotId`, `agentIds`, `createdById`, `cancelledById`) and refuse an org member that names an agent of another org with the same label (`RBAC_DENIED`, `assignee-not-on-roster` / `actor-not-on-roster` for a pilot or creator, `participant-not-an-agent-of-org` for a participant). The creator-only cancel compares agent IDs: a different agent that now carries the creator's label cannot cancel, the creator renamed still can. `missions:get` and `missions:list` serve an org member the rows of its own org whose `pilotId` is on its roster by ID; the `list` pilot filter is an ID (`by_pilotId_status`, `by_orgId_pilotId_status`; `missions` is at 14 indexes), so a label never selects the pilots of two orgs, and a label naming no agent is an empty success. Anonymous callers are still refused `RBAC_DENIED`. `create` and `update` accept `verifiedActor` and the MCP forwards it. New internal migration `migrations/backfill_mission_actor_ids` (dry run by default, paginated, unknown or ambiguous labels listed as `blocked`, never guessed). Deploy order: run the migration first, because a row without IDs names nobody (org members stop reading it, nobody cancels it as creator), then Convex, then the MCP. Evidence: `convex/__tests__/missionsById.test.ts` 13/13 (9 red on the previous head), `convex/__tests__/backfillMissionActorIds.test.ts`.
