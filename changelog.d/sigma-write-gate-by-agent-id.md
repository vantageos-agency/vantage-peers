- **A person token whose agent was added to the organisation after the person connected can write without reconnecting (VantagePeers Cloud).** The write gate (`from` / `createdBy` / `callerOrchestrator`) compared the acting name to the label roster minted onto the token (`oauth_access_tokens.fromAllowList`), case-sensitively; an agent added afterwards, or listed lower-case while stored capitalised, was refused ("from=... is not in this client's allowlist"). For a person token acting as an agent resolved by ID, Convex now returns `personalAgent.onRoster` (the agent's ID in the org mapping's `allowedAgentIds`, read live in `oauth:getAccessTokenByHash`) and the MCP admits the write iff it is true and the name is that agent's stored name. Callers with no agent ID (legacy label bearers, seats, master) are unchanged; a mapping with no roster by ID lists nobody (refused by default, as every other roster-by-ID door). `clientOrgMapping:addRosterMembers` appends the agent's exact stored name. Rollout: Convex first, then MCP; no contract bump (additive return field); existing tokens need no reconnect. Pinned by `convex/__tests__/personalAgentOnRoster.test.ts` and `mcp-server/test/write-gate-by-agent-id.test.ts`.
