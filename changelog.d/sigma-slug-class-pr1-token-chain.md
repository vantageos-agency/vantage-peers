- **The OAuth token chain no longer resolves, mints, refreshes or gates by an organisation slug (VantagePeers Cloud, slug-class sweep PR 1 of 4).** `oauth:getAccessTokenByHash` read the token's organisation through its mint-time slug, so after an organisation was renamed and another took the slug, the old token answered the NEW holder's permanent ID (the MCP then admitted that organisation's `team/<id>` namespace) and handed every label-keyed door the stale slug. It now reads the mapping by the token's `clerkOrgId` and returns that organisation's current slug; a token row naming an organisation by slug only is refused (prod measured: 0 of 28 live access tokens lack `clerkOrgId`). `oauth:createAccessToken` and the refresh mint stamp the ID from a verified source (consent code, scope profile, refreshed family) and refuse with `MINT_ORG_ID_REQUIRED` when none carries one, instead of deriving it from the slug's current holder. `oauth:rotateRefreshToken` judges a person family's membership by the family's own `clerkOrgId`, not the caller-sent label. `orgRoster:getForAccessToken` keys on `token.clerkOrgId`. The `verifiedOrg` row gate (`assertRowInVerifiedOrg`) compares permanent IDs, so the new holder of a released slug could no longer act on the former holder's tasks through the service account, and the renamed former holder reaches its own. Convex only, no argument or return shape change, no contract bump. Pinned by `convex/__tests__/slugTakeoverTokenChain.test.ts`; remaining sites of the class are A-6..A-27 of `analysis/slug-class-sweep-2026-11-01.md`.
